分清四类成本：

## 3. 风险清单：不是都已证实为 bug

### 已有复现与回归

断层由整屏补空行造成，`fbe0dcb` 已改为只替换实际尾部。回归位于 `tests/native-tail-terminal.test.ts`；旧实现失败，新实现通过，覆盖恢复、增长、settled 收缩、编辑和新消息。继续检查 screen 与 scrollback 的连续行，不能过滤空行后再比对。

### 高优先级待验证

1. **部分交付后取消**：超大段前 256 行已写成功，整体 receipt 仍 pending；取消后是否遗失交付进度？用慢 sink 在第二批前取消，再追加或修订节点。区分有标记更正与无意重发。
2. **来源删除与重排**：当前调和侧重存在的可见节点；已提交节点被删除、隐藏或换序时是否缺少说明？用同 key 修订、删除再插入、同长度内容替换验证。用户折叠是展示变化，不能误报为源码删除。
3. **准备阶段无界**：一个 10 万行节点可能先生成全部 rows，再分批写。对比一个大节点与很多小节点，测首批交付时间、最大暂停和准备内存，而非只测持续帧。
4. **混合节点**：单文本 fixture 不代表思考/正文/工具/元信息混合节点。检查是否一直等待 settled 才提交。
5. **跨写入的 resize**：入队尺寸、真正交付尺寸和当前布局可能不同；用可控制释放的 sink，在交付前和交付后 resize。不要无效化旧代次后却仍发布旧坐标。
6. **独立控制输出**：回放标记、会话分隔符、背景和终端模式控制都走 control，但并非每种字节都不移动光标。列出生产调用点，验证移动光标的控制是否同时更新或废弃 anchor。
7. **帧与交互几何**：pi 的 onAfterRender 先发布几何，而实际写入可能被背压拖延；tailRow 也未必是零。用慢写入 + overlay 开闭验证“看见的是哪一帧、命中的是哪一帧”。这不是菜单滚轮故障的已证实原因。
8. **图片协议生命周期**：candidate hook 提前返回会跳过后续 pi 图片 ID 收集/清理。先审计 Kitty 等图片能力实际使用范围，再做图片出现、替换、resize、模式切换和退出测试；不要假设文本 xterm 测试覆盖图片。
9. **异常同步输出恢复**：frame 使用 2026 包围写入；中途失败时是否留下同步更新或光标状态？验证正常恢复、失败恢复和不能继续写入时的边界。不通过“重发正文”恢复终端。
10. **历史加载完成判定**：现有加载逻辑比较节点数量是否进展。分页可能消耗了事件却不增加可见节点；用官方行为或合成 API 验证，不能立即假定一定是 bug，也不能拿长度启发式作为完整性证明。

其中确证的问题应先补失败测试，再选择最小安全修复；证伪的风险从必修列表移出，保留调查记录。菜单滚轮观察项不要求跨终端穷举到“找到原因”为止。

## 4. 建议实现路线与取舍

### 4.1 来源单元、片段与交付账本

建议概念：SourceUnit、PreparedSegment、DeliveryReceipt、PresentedFrame。它们可以合并或换名，关键是职责清楚：来源是谁、准备了什么、实际交付多少、屏幕展示哪一帧。

- 以官方节点 key 为外层身份，内部按原文位置/内容类型定位。若官方未给子块稳定 ID，不发明一个 revision；索引只有在精确来源验证后才可复用。结构插入导致定位失效时退回节点级更正。
- 分开正文、思考、工具与装饰，不再以 `rows.length === 1` 判断能否增量。未支持分段的组件可继续保持整体可变，不强行泛化。
- 源偏移使用 UTF-16，并验证边界不切开代理对、CRLF 或转义单元。保留规范化到原文的映射。
- 记录段内已交付片段；一个源码行折成多行时，完整源码覆盖与显示片段进度是不同概念。取消不得忘掉已交付部分。
- 准备状态与提交状态分离。任何提前计算的解析/高亮游标都不能因为 reserve 就成为已提交状态。
- settled 核对所有来源单元及最终范围，不仅核对总长度。legacy `__partial__` 缺少 durable identity 时仍保守等待。
- 删除、隐藏、重排及修订用带来源的追加更正解释；回放按权威顺序重新输出。不要为了像“没有发生过修改”而擦除历史。

来源元数据随历史增长可以接受，但必须给出内存组成与释放时机；不能为了省账本而牺牲精确性，也不应额外长期保存完整高亮历史副本。

### 4.2 准备与队列真正分批

- 交付确认更新受影响的 key，不全量重建候选索引；权威顺序变化才做必要的顺序调和。
- 历史准备尽可能惰性产生块/行。现有 256 行批次可作为起点，而不是不可调整的常数。
- 准备阶段在可恢复边界让出执行权。约 4ms 可以作为初始调度目标，不是 JS 同步 parser 的保证。
- 单个巨大、不稳定语法单元需单独测量。先考虑更小的合法工作单元；只有实测显示同步工作阻塞且无法分解，再考虑 worker/独立解析调度。引入时补 worker 生命周期、打包、取消和故障测试。
- 慢输出时限制预取；合并可替换尾帧，不合并丢弃正文、审批、错误、结束和必须有序的控制事件。
- 正在写入的旧代次事务不可能撤回已经交付的字节。明确边界：取消尚未开始的任务，等待/隔离在途交付，分隔标记之后不能再写旧会话任务。

历史分页从新到旧时，不直接将每一页追加到终端。先建立可靠的历史顺序再输出，同时保留加载进度和取消。加载中到来的新事件由 Harness 保存，显示层不要另建 Session 数据库；输出遵守顺序屏障。取消后明确显示不完整，不能伪装完整恢复。

### 4.3 Markdown：共享规则，但不要把 renderer 当流式 parser

优先复用当前 pi Markdown 的 Marked 实例配置、StrictStrikethroughTokenizer、样式规则及选择映射。私有包内 hook 或提取适配器均可；避免一份复制后悄悄漂移的 renderer。

稳定性不仅是“出现空行”：

| 类型 | 安全起点与要防的后续变化 |
| --- | --- |
| 段落/标题 | Setext、未闭合 inline、下一块决定的分隔空行 |
| 列表 | 后续 item、loose/tight 变化、缩进和容器继续 |
| 引用 | lazy continuation、嵌套块与退出容器 |
| 表格 | 后续行会改变列宽；闭合前不冻结最终宽度 |
| 围栏代码 | 确认围栏与容器后按完整源码行推进；保留语言与缩进 |
| 引用链接 | 保留所在文档定义与依赖；后到定义可影响此前内容 |
| HTML/不确定扩展 | 未证明稳定就留尾部，settled 必须完整输出 |

块间空白应由共享上下文产生一次，不让每段独立 Markdown 渲染各自产生间隔。定义作用域遵循真实文档单元，不能错误跨工具或节点共享链接定义。

长期不闭合表格/列表可能只能保持可变。这不等于实现失败；但其 A 成本不能被称为已解决。若改变表格流式展示策略会改变用户体验，先提出具体对照，不自行冻结错误宽度。

### 4.4 高亮只返回本次新增内容

- 每个代码块保留独立 GrammarState 和最后完整行位置，避免同语言流互相挤占。
- 候选接口接收调和后确认的新增行与未完成尾行，返回本批行；移除候选调用链中的整段源码缓存键和完整结果数组复制。
- 原接口保留给旧路径、full 模式和其他使用者，减少兼容改动。
- 未完成行从最近完整状态重新解析；非追加修订明确失效范围，必要时重建，成本另报。
- 主题、语言加载和 GrammarState 的关联以 Shiki 实际契约为准。不要无证据认定换主题永远可复用；不能复用时重建语法状态，但不重写已提交历史。
- 语言延迟加载后只更新未提交内容。关闭块、切换代次、取消和退出释放可释放状态。

**特别注意：**即使以后获得 changedKeys，官方若仍仅给完整活动字符串，确认追加仍有比较成本。把“高亮随 D”与“来源调和随整段正文”分开，不能暗示都解决了。

### 4.5 以已交付帧统一坐标，保留文本来源

- 只有写入成功才发布该帧的几何，至少包括代次、尺寸、tailRow、slice offset、cursor 和 overlay 信息。
- 帧尚未展示时，交互继续使用已展示帧或暂时无命中区域，不能使用未来坐标激活错误项。
- 将控制事务分为不移动布局的协议控制、改变光标/布局的控制和模式切换；不用通用 ANSI 猜测器替代清晰的生产调用契约。
- resize 可失效坐标，从安全新行重建；允许终端自身 reflow，不能清屏掩盖错位。
- 复制所需映射区分源空白、展示填充、硬换行和视觉折行。不能通用 trim；不能把 Canvas 全宽字符串当原文。
- 可以尝试用擦除/背景控制替代填充字符，但是否改善复制需真实终端验证；空白单元也可能被终端复制。不要仅看 stripAnsi 测试。
- 复制可见文本不等于还原所有 Markdown 语法标记。代码原有缩进、尾空格和换行另有精确断言。

### 4.6 官方接口依赖：需求而非虚构 API

当前公开契约不足以准确定位历史修订。继续精确扫描，单独显示成本。未来核对是否获得与权威快照一致的变更批次，覆盖新增、更新、删除、可见性、顺序、重置、缺口和读取时机。

若想避免完整活动正文比较，还需可靠的追加/范围修订信息或等价不可变分块保证。新 API 的命名和形态由官方决定，不能预先实现一个假定字段。

本轮只维护依赖说明和最小成本复现。禁止私有 monkey patch、直接接管原始日志折叠或放宽一致性来“解除阻塞”。

## 5. 怎样证明修好了

### 测试分层

1. **纯状态测试**：reserve/deliver/cancel/fail、来源修订、代次隔离；控制 sink 可逐批释放。
2. **真实投影测试**：至少一个思考→正文→工具→正文的真实形状 fixture，不只使用单文本 assistant。
3. **虚拟终端端到端**：Transcript→Canvas/Markdown→pi hook→NativeOutput→xterm，核对 screen、scrollback、光标和原文覆盖，不只检查字符串里“包含某段”。
4. **实际 PTY**：最终打包内容运行，Windows ConPTY、Debian PTY、独立 tmux；确认实际打开的启动器与包 hash。
5. **人工终端验收**：UU 横竖屏、键盘开关、历史加载、回看、复制。图片协议必须使用支持该协议的终端验证，不能用文本模拟器代替。

场景应组合而不是只各测一次：慢写入+取消；部分交付+修订；resize+菜单；回放+Session 切换；换主题+开放代码块；同语言双代码流；单行超过视口宽度+中文/Emoji；巨大节点+恢复取消。

增加随机但可重现的操作序列（保存 seed）：追加、修订、settled、重复通知、切换代次、释放 sink。采用独立原文/事务 oracle，失败时缩减为最小 fixture；不能让生产实现自己生成 expected。

固定配置、无修订时，候选应与权威完整渲染在语义和承诺的布局上等价。更正场景允许旧版本留在 scrollback，但必须标明来源；新回放必须是当前权威版本。
