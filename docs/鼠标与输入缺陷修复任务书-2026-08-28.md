## 1. 任务目标

一次性收敛 Windows Terminal 实测暴露的 7 类输入与鼠标问题，同时保持 SeekTTY 是 Harness 的薄终端 Surface，不取得 Agent、Session、Provider、Settings、Credential、Profile、插件或持久化状态的所有权。

本任务只允许在用户明确批准后实施。本文件完成、审计和提交规划不构成开工授权。

## 3. 审计证据与根因

### 3.1 B1：鼠标语义被错误地重新编码成普通文本

- 触发：在 `/model` 等带搜索输入的 overlay、Settings SecretInput 或主 composer 上悬停鼠标并滚轮；可见输入会出现重复 `up`/`down`，SecretInput 则发生不可见污染。
- `src/client/overlays.ts:1127-1135` 把 wheel 转为 `Key.up` / `Key.down` 后调用活动组件的 `handleInput()`。
- `src/client/surface.ts:1164-1167` 对主 composer 做同样处理。
- pi-tui 的 `Key.down` 是键位标识字符串 `"down"`，不是方向键字节 `\x1b[B`；`matchesKey("down", Key.down)` 为 false，输入组件会把它当作可打印文本。
- 影响不止截图中的模型搜索：TextInput、SecretInput、SearchSelect、MultiSelect 和主 composer 都可能被污染；SecretInput 中污染不可见，风险最高。
- ScrollableDetailOverlay 同样收不到有效方向键，所以 overlay wheel 可能完全无效。

### 3.2 B2：Enter 已提交，但 UI 进入无反馈的异步空窗

- 触发：首次进入 provider onboarding，输入 API Key 后按 Enter；或在 Settings 的 Credential 编辑页重复该流程。输入页立即消失，保存期间继续按 Enter 没有 busy/成功/失败反馈，随后配置状态可能才异步变化。
- 临时组件探针中 `SecretInputOverlay` 的 `Input.onSubmit` 能识别 Windows Terminal 的 `\r`；仓内尚无 CR/LF/CSI-u Enter 的行为测试，因此这只能排除一个简单假设，不能证明真实 Surface 全链路正常。
- `src/client/overlays.ts:1023-1042` 在 submit 时立即移除输入页，然后才让调用方执行异步保存。
- 当前 Secret prompt 并不经过 `src/client/overlays.ts:868-890` 的 busy 分支；B2 的现有根因是输入页拆除后的主界面异步空窗，而不是 busy page 吞键。修复后若复用该 busy 机制，则必须让 busy 状态可见，并对重复 Enter 给出稳定反馈。
- onboarding 在 `src/client/provider-onboarding.ts:274-308` 执行 credential set、重新 describe 和 success notice，中间没有稳定的保存/验证页面。
- onboarding 使用 `normalizeOnboardingApiKey()`；Settings 的 `src/client/actions.ts:2444-2458` 直接把原始 Secret 传给 `setCredential()`，没有复用同一校验，可能保存变量赋值、引号、换行或 wheel 注入文本。
- plugin catalog Credential 的 `src/client/actions.ts:3066-3080` 也使用独立的原始 Secret 写入路径；共享事务必须覆盖这些 Settings 写入口，但只能对已识别的 provider/ref 套用对应校验器，不能把 DeepSeek 格式强加给任意 Credential。
- `providerUsable()` 只能看到 Harness 提供的 value-free `configured/source/writable` 元数据；`configured` 不能等同于 key 已通过真实 Provider 请求。

### 3.3 B3：release 丢失 origin，ANSI reset 又切断高亮

- 触发：在 full mouse 模式下，从 transcript 或 composer 的一个位置拖到另一个位置；跨 Markdown inline code、彩色 token 或链接时可在拖动中看到高亮断续，松开左键后选区缩成一点或消失。右键拖动也可错误进入同一路径。
- `src/client/mouse-controller.ts:320-367` 的 drag update 带 `origin`。
- `src/client/mouse-controller.ts:370-397` 的 ended drag 丢失 `origin`。
- `src/client/surface.ts:1181-1186` 在 release 时重新应用选择；没有 origin 后 transcript 退化成单字符，composer 会清空 selection，copy-on-select 随后复制错误范围。
- `handleDrag()` 未限制左键，右键拖动也会进入 selecting，与旧任务书“右键只复制已有选区”冲突。
- `src/client/text-selection.ts:257-286` 只在选区开始处写一次 `SGR 7`；原文本内的 `SGR 0/27`、前景/背景重置会取消反显且没有重新施加，Markdown link、inline code、Shiki token 因此出现断续高亮。
- `anchorAtCell()` 默认只产生 `before` affinity，拖动终点字符可能被排除。
- `ownerTextFromRenderedLines()` 用“是否填满 content width”猜测软换行；真实换行恰好占满整行时可能被误拼接。该边界必须与 B3 一起补测试，不能继续用宽度启发式宣称字节级正确。

### 3.4 B4：toggle 被按普通一次性 button 抑制

- 触发：点击工具卡左侧可点击标记将其展开，并在 400ms 内再次点击同一标记；第二击被吞掉，无法立即收回。
- `src/client/mouse-controller.ts:401-420` 统计 400ms 内的重复点击，并对所有 `role === 'button'` 的第二/三击设置 `suppressed`。
- `src/client/surface.ts:1043` 在工具卡 toggle 之前直接返回。
- 工具卡内部 `pointerToggleTool()` / `toggleToolCard()` 的展开、收回逻辑本身正常。
- 现有测试只验证一次 pointer expand，没有验证第二次 pointer collapse。

### 3.5 B5：autocomplete 视觉窗口没有进入 hit snapshot

- 触发：输入 `/`，让候选数量超过一个可见窗口；滚轮移动到第二个窗口，再点击其中任意可见行。实际 focus/补全仍落到第一页的同一相对行，scroll-info 行也可能被当成候选。
- `PromptEditor.lastLocalGeometry()` 只暴露整个 autocomplete rectangle。
- `src/client/surface.ts:380-388` 只注册一个 autocomplete HitRegion。
- `src/client/surface.ts:1113` 把点击的可见行直接作为全量候选绝对 index，忽略 SelectList 的 `startIndex`。
- autocomplete 的 scroll-info footer 也计入 rectangle，当前可被错误解释为候选行。
- `mouseArmed` 使用 `String(index)`，而非稳定 item identity；wheel、键盘输入、异步候选刷新、Session/模式变化时没有统一失效，存在二次点击执行不同命令的安全风险。

### 3.6 B6：当前终端协议收不到 hover

- 触发：full mouse 模式下仅移动鼠标经过工具卡、autocomplete option、overlay option 或底栏按钮，不按键；目标没有视觉变化。
- `src/client/mouse-protocol.ts:74-83` 启用 `1002 + 1004 + 1006` 并显式关闭 `1003`。
- `1002` 只报告 press/release/button-motion，普通无按钮移动不会到达应用。
- 即使直接打开 `1003`，当前 `src/client/mouse-protocol.ts:142-144` 也会把 no-button motion 解码为 `drag`/`button: none`；必须先增加独立 `move` 语义，不能只改私有模式序列。
- 旧任务书明确写明“不依赖 hover”，相关 tests 还断言不得包含 `1003h`。
- 因此 B6 不能只靠换颜色解决，必须修改协议、状态机、行为 Settings 和性能门禁。

### 3.7 B7：键盘 Enter 的组件路径存在，但没有真实 Surface 门禁

- 触发：输入 `/`，用方向键改变高亮候选后直接按 Enter。用户实测未执行；当前孤立 Editor 探针可以执行，因此必须在 packed candidate 的真实 Surface/PTY 上复现，不能先把它定性为 Editor Enter 解析错误。
- 当前 pi-tui Editor 对 slash prefix 的 Enter 会 apply completion 后继续 submit；组件探针 `/`、Down、Enter 能提交 `/settings`。
- `src/client/surface.ts:1126` 的鼠标二次点击调用 `applyAutocompleteSelection()`，该 patch API 只填入并关闭列表，不提交命令。
- `tests/mouse-clicks.test.ts` 只读取源码并搜索函数名，不能证明任何点击或 Enter 行为。
- 最终修复不得假定用户观察错误；必须用 packed candidate + PTY 的本地 slash command 复现或证伪，并让键盘与鼠标走同一 activation contract。

## 4. 本任务替代的旧规格

本文件经批准后，替代 `docs/完整鼠标架构与点击命中系统-任务书.md` 中以下规则：

1. “所有 button 在 400ms 内抑制重复激活”改为按目标声明 activation policy。
2. “禁止 `1003`、不依赖 hover”改为受控 hover reporting，允许用户关闭。
3. “右键不模拟上下文菜单”改为应用内安全菜单；仍不尝试调用 emulator 原生菜单。
4. “autocomplete 第二击或 Enter 执行”由明确、可测试的统一 activation API 实现，不再靠视觉行号或私有字段推断。
5. 旧稿 4.3 “后续提交不得反复改同一补丁接口”在本任务中由两个互不混杂的、精确绑定 `@mariozechner/pi-tui@0.73.1` 的窗口替代：Commit 2 只补齐 Editor selection 绘制/替换公共接口，Commit 4 只补齐 autocomplete snapshot/activate 公共接口；其他提交不得修改该 patch，Commit 4 完成后整体重新冻结。Surface 始终禁止访问 `selectionRange`、`autocompleteList` 等私有字段。

危险确认仍只允许 Enter；该安全规则不变。

## 5. 最终架构决策

### 5.1 严格分离原始输入和语义动作

数据流固定为：

```text
terminal bytes
  -> MouseProtocolDecoder
  -> MouseInput
  -> MouseController / hover coalescer
  -> MouseSemanticEvent
  -> typed target operation
```

禁止任何 wheel/click/hover 路径调用 `handleInput(Key.*)`。只有真实键盘 leftover 可以进入 pi-tui `handleInput()`。

Overlay 增加可选语义接口：

```ts
interface OverlayMouseTarget {
  handleWheel?(lines: number, point: CellPoint): boolean
  handleOptionClick?(optionId: string): OverlayMouseClickResult
}
```

- SearchSelect/MultiSelect 直接移动 SelectList index。
- ScrollableDetail 直接修改 offset。
- TextInput/SecretInput 对 wheel 返回 consumed 且不改 value。
- 普通 composer input 对 wheel 不做字符或 cursor 注入。

### 5.2 HitRegion 声明交互策略，而不是依赖通用 role

扩展为等价的强类型信息：

```ts
type ActivationPolicy =
  | 'none'
  | 'toggle'
  | 'focus-then-activate'
  | 'single-shot'
  | 'enter-only'

type HoverStyle = 'none' | 'button' | 'option' | 'text'
```

- 工具卡：`toggle`。
- 普通 autocomplete/overlay option：`focus-then-activate`。
- submit/delete：`single-shot`，且继续受 FocusOut→FocusIn 与 250ms guard 保护。
- danger/permission：`enter-only`。
- 双/三击粒度只用于 text，不再全局抑制 button。

### 5.3 Armed target 必须绑定稳定身份

Armed token 至少包含：

```ts
{
  kind: 'example' | 'autocomplete' | 'option'
  targetId: string
  contentGeneration: number
  armedAt: number
}
```

wheel、drag、普通键盘输入、autocomplete refresh、overlay replace、Session change、mouse mode change、FocusOut、resize 和超时必须使 token 失效。没有稳定 item ID/content generation 时，鼠标只能 focus，不能执行。

### 5.4 Selection 是一个贯穿 press/update/end 的事务

- 只有左键可以建立或扩展选择。
- semantic selection event 的 update/end 都携带相同 origin、owner 和 button。
- release 只提交最终 focus，不得重建 anchor。
- forward/reverse drag 正确设置 before/after affinity，使指针所在 grapheme 按预期包含。
- copy-on-select 在最终 selection 提交后运行；复制成功不清高亮。
- Session/owner 删除、Escape 或显式 clear 才清理 selection。

高亮绘制必须对 ANSI token 化：选区内遇到任意 SGR reset/change 后重新施加 selection layer，离开选区时恢复原样式。处理量继续限制在当前 viewport，禁止为高亮重新 render 全历史 owner。

Composer 不能只在 Surface 保存一个逻辑范围：Commit 2 必须通过精确 pi-tui patch/adapter 让 Editor 公开 selection render/replace 语义。可见选区由 Editor 自身在 render 阶段绘制；普通输入、Backspace、Delete、bracketed paste 和 submit 在组件内部先消费/替换 selection。Surface 只传 semantic anchor/focus，不读取或修改 Editor 私有 `selectionRange`。

### 5.5 右键使用应用内安全菜单

完整鼠标模式下不可能可靠要求 Windows Terminal/iTerm2 弹出原生菜单，因此实现 SeekTTY 自有菜单：

- transcript 有选区：`复制`、`切换到原生选择模式`、`取消`。
- composer 有选区：`复制`、`粘贴纯文本`、`取消`。
- composer 无选区：`粘贴纯文本`、`切换到原生选择模式`、`取消`。
- transcript 无选区：不自动粘贴，只提供原生模式和取消。

菜单作为临时 capturing overlay 在右键坐标附近打开并限制在 viewport 内；方向键/Enter 与鼠标使用同一 option identity，Escape、选择“取消”、模式切换、FocusOut 或 Session/overlay 替换时关闭。菜单打开和关闭不得清除已有 selection；点击菜单外只关闭并消费事件，不把同一次 release 透传给底层目标。

新增 clipboard text reader 时必须：

- 使用平台命令 seam 和 deadline；不执行剪贴板内容。
- 限制 UTF-8 字节数，拒绝 NUL/C0/C1/终端 escape，复用现有 paste sanitation。
- 不记录内容、长度以外的可识别信息或子进程 stderr。
- 平台 reader 不可用时禁用 Paste 并显示安全原因。
- 不在本任务中实现自动 middle-click paste 或读取远端 OSC 52 clipboard。

### 5.6 Hover 使用可关闭的受控 `1003`

在通过 Harness Settings 持久化的 `seektty-behavior` 中新增 `hoverFeedback: boolean`，默认 true：

- `mouseMode=full && hoverFeedback=true`：显式关闭 `1000/1002/1007`，启用 `1003/1004/1006`。
- `mouseMode=full && hoverFeedback=false`：保留 `1002/1004/1006`。
- `mouseMode=native`：关闭全部 mouse/focus private modes。

decoder 将无按钮 motion 解码为 `move`，不能伪装成 drag。连续 move 只保留最后坐标；只有 hovered target ID 改变时才 render。FocusOut、resize、overlay/session replace 和 mode change 清理 hover。

hover 只提供视觉提示，不触发 focus、armed 或 action：button/tool toggle 提高前景与边框/标记对比度，option 使用主题化行高亮，scrollbar thumb 提亮；danger/permission 不提供“可鼠标确认”的暗示。终端鼠标指针形状不在 TUI 控制范围内，不伪造 GUI cursor。

### 5.7 Autocomplete 使用同一份渲染快照完成 hit test 和激活

精确版本 pi-tui patch 一次性增加等价公共 API：

```ts
interface AutocompleteSnapshot {
  generation: number
  selectedIndex: number
  visibleRows: readonly {
    visualRow: number
    absoluteIndex: number
    itemId: string
    selectable: boolean
  }[]
}

moveAutocompleteSelection(delta: number): boolean
activateAutocompleteSelection(source: 'enter' | 'mouse'): {
  applied: boolean
  submitText?: string
}
```

- Surface 为每个 visible option 注册独立 HitRegion。
- scroll-info footer 不注册 option。
- click 使用 item ID + generation，不用视觉 row 重新推算。
- Tab 只补全；slash command 的 Enter/第二次安全鼠标点击补全并提交一次；文件/path completion 只补全。
- Surface 不访问 pi-tui 私有字段，不直接调用过时 `onSubmit()`，由 adapter 原子返回 post-completion submit text。

### 5.8 Credential 输入使用统一事务

首次 onboarding、Settings Credential 和 plugin catalog Credential 复用同一个 value-free credential editor controller；事务、busy、去重和 redaction 共用，校验器按已识别的 provider/ref 注册，未知通用 Credential 不误套 DeepSeek 规则：

1. 本地按 ref/provider 选择校验器；DeepSeek ref 使用 `normalizeOnboardingApiKey()`。
2. Enter 后立即展示不可重复提交的 busy page。
3. 通过 Harness Credential API 写入；不读取返回值。
4. 重新 describe `configured/source/writable`。
5. 成功显示明确状态；失败在同一流程显示具体、无 Secret 的错误并允许重试。
6. `source=env` 且不可写时明确提示启动环境正在覆盖本地文件层。

不得为了“验证可用”自动发送付费模型请求。第一次真实请求仍由 Harness 权威判定 credential 是否能用于 Provider。

### 13.2 正常桌面交互约定与最终语义

外部规范支持“选择”和“激活”分离：Windows 的鼠标交互指南规定 selectable object 使用单击选择、双击打开；List Box 指南把双击定义为“选择项目并执行默认命令”；ItemsView 也把 mouse click 的 selection 与 item invocation 分开。Apple HIG 同样把 hover effect 与 focus/selection 区分，并建议在激活会导致上下文切换时使用独立手势。

参考：

- <https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-mouse>
- <https://learn.microsoft.com/en-us/windows/win32/uxguide/ctrl-list-boxes>
- <https://learn.microsoft.com/en-my/windows/apps/design/controls/itemsview>
- <https://developer.apple.com/design/human-interface-guidelines/focus-and-selection/>

SeekTTY 的 slash command 候选不是无副作用的普通下拉值；它可能切换 Session、Settings、权限或其他状态。因此不采用“首次单击立即执行”的网页 autocomplete 语义，最终行为固定为：

1. hover 只提供弱视觉预览，不改变 selected item、不 armed、不执行。
2. 第一次左键单击一个 stable item ID：选中、armed、立即重绘，但不执行。
3. 同一 item ID + generation 上的第二次单击激活；原生双击会自然产生两次 click，且只允许激活一次。
4. 点击另一个候选只切换选中项并重新 armed，不能沿用前一项的 armed token。
5. 键盘 Enter 激活当前选择；Tab 只补全。候选是 path completion 时即使鼠标二击也只补全，不误提交。
6. wheel、普通键盘输入、候选 refresh、FocusOut、resize、mode/Session/overlay change 或 1500ms 超时清除 armed token。
7. 即使某项已经由方向键预选，第一次鼠标单击仍只建立鼠标 armed 状态，避免“用户只是把焦点移到鼠标，命令却立即执行”。

这正是当前代码想表达的语义，不需要把 autocomplete 重写成新的点击模型。

### 13.3 B8 根因：selection 已改变，但 release 后没有请求重绘

触发方式：

1. 输入 `/` 打开候选列表。
2. 移动鼠标使某一项进入 hover。
3. 单击另一项并松开；视觉上没有稳定显示新的 selected row。
4. 再次单击或产生另一个会触发 render 的输入后，选中/激活状态才变得可见，因此体感上像“双击才能选中”。

代码证据：

- `src/client/surface.ts:1309-1330` 已先调用 `selectAutocompleteItem(generation, itemId)`；第一次 click 会在 `1320` armed 后返回，第二次才调用 `activateAutocompleteSelection('mouse')`。所以业务状态机不是“双击才选择”。
- `src/client/mouse-activation.ts:3-34` 用 stable kind/item ID/generation 和 1500ms TTL 保护第二次激活；click count 本身不参与 autocomplete 执行。
- `src/client/surface.ts:1358-1410` 只有 `needMouseRender=true` 才在 mouse batch 结尾 render；click 分支 `1380-1382` 调用 `dispatchMouseClick()` 后没有设置该标记。
- hover 常在 press 时由 `src/client/surface.ts:1360-1362` 清除并提前 render；随后独立到达的 release 虽然改变 autocomplete selection，却没有新的 render invalidation。若 press/release 恰好在同一输入 chunk，问题可能不出现，所以表现具有时序性。
- `src/client/chrome.ts:525-534` 又把 hover row 直接套用 `background.selection()`；hover 与真实 selection 的视觉层级接近，放大了“第一次 click 没有效果”的错觉。
- `tests/autocomplete-mouse.test.ts:74-88` 只证明 adapter 能按 identity 改 index；`tests/mouse-clicks.test.ts:7-25` 仍是源码字符串检查。当前没有 Surface 级测试覆盖“move、press、release 分三个 chunk 到达，release 后必须 render 且不能 submit”。

最优修复方向：

1. 不改现有 focus-then-activate 状态机。
2. 让 `dispatchMouseClick()` 返回同步 UI 是否变化，或在每个 semantic click 后无条件设置 `needMouseRender=true`。后者最简单稳健：mouse batch 仍只合并成一次 render，而物理 click 频率远低于 `1003` move，不会恢复 hover flood 卡顿。
3. 把 hover 和 selected 明确分层：hover 使用较弱、主题化的 preview；selected 保留箭头/强背景；armed 继续以 selected 状态呈现。hover 不得显示 selection arrow。
4. 增加真实 Surface integration test，而不是继续添加源码字符串断言：
   - hover 不选择、不 armed；
   - 分离输入 chunk 的首次 click 更新 selection、请求一次 render、提交次数为 0；
   - 同一 identity 的第二次 click 只提交一次；
   - 改点另一项、过期、refresh、wheel、FocusOut 后必须重新第一次单击；
   - double click 不能形成两次 submit；
   - `hoverFeedback=false` 时首次 click 仍必须可见。

影响评估：

- runtime 影响低：每个 click 最多增加一次合帧后的 render，不增加 move/hover 事件量。
- 不改变 HitRegion、generation、path completion、danger Enter-only 或 Harness 所有权。
- hover 配色会影响主题/snapshot，需要检查深色、浅色、无色终端；这是视觉回归面，不是交互安全风险。
- 若反过来改成首次 click 直接执行，事故面明显增大且违反上述桌面列表约定，不采用。

### 13.4 B9 根因与三端统一修复架构

触发方式：

1. 在 full mouse 模式拖选含中文的 transcript 文本。
2. 右键打开 SeekTTY 的 `文本操作`，选择 `复制`。
3. 粘贴到任意 Unicode 应用；得到类似 `璇峰憡璇夋垜浣犳兂鍋氫粈涔堬紵鍏朵粬寮€鍙戜换鍔★紵` 的 mojibake。
4. 切换 native selection 后使用 Windows Terminal 自身复制则正常。

代码证据：

- `src/client/surface.ts:1083-1113` 从 transcript/composer 取得 `selectionText` 后原样传给 `copyText()`；这里没有 codec 转换。
- `src/client/transcript.ts:1562-1571` 和 `src/client/text-selection.ts` 都在 JS Unicode string 上提取选区，没有把文本转成 GBK。
- `src/client/clipboard.ts:261-263` 的 OSC 52 路径明确使用 UTF-8，编码正确。
- `src/client/clipboard.ts:50-63` 的 Windows writer 却是 `clip.exe`；`src/client/clipboard.ts:99-128` 把 JS string 直接交给 child stdin，Node 写出 UTF-8 bytes，而 `clip.exe` 没有 UTF-8 输入契约，会按 Windows console/活动代码页解释重定向字节。
- 同一文件的 Windows reader 在 `src/client/clipboard.ts:73-91` 明确把 PowerShell stdout 设成 UTF-8；所以当前 read 和 write 确实不对称。
- 默认 `clipboardFallback='auto'`。`src/client/clipboard.ts:271-293` 会先写正确的 OSC 52，再继续调用平台 fallback；`clip.exe` 成功后会覆盖前者，而且函数仍返回 `osc52`，掩盖最终实际写入者。
- 合成验证可精确复现特征：把 `请告诉我你想做什么？其他开发任务？` 的 UTF-8 bytes 当 GBK 解码，得到上述 `璇峰憡...` 字符串。因此证据指向 writer codec，而不是选区宽字符映射。

Windows 官方文档只说明 `clip` 接收管道输入，没有承诺 UTF-8；PowerShell 文档则明确说明 Windows PowerShell 的编码默认值并不一致，`Default` 使用活动代码页。`Set-Clipboard -Value` 接收 .NET string，可作为受控 Unicode 写入端：

- <https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/clip>
- <https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-7.6>
- <https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/set-clipboard?view=powershell-7.5>

统一原则不是在三端各写一套 string 特例，而是在 platform adapter 之前只生成一次 `Buffer.from(text, 'utf8')`，然后让每个固定 writer 明确声明“这些 stdin bytes 是 UTF-8 文本”。建议内部契约为等价结构：

```ts
interface ClipboardWriterSpec {
  readonly method: 'powershell' | 'pbcopy' | 'wl-copy' | 'xclip'
  readonly command: string
  readonly args: readonly string[]
  readonly env?: Readonly<Record<string, string>>
}

interface ClipboardWriteResult {
  readonly finalMethod: 'osc52' | ClipboardWriterSpec['method']
  readonly succeeded: readonly ('osc52' | ClipboardWriterSpec['method'])[]
}
```

三端固定后端：

| 平台 | writer | UTF-8 契约 | 失败后行为 |
| --- | --- | --- | --- |
| Windows / Cygwin | `powershell.exe -NoLogo -NoProfile -NonInteractive -Command <固定脚本>` | `UTF8Encoding(false, true)` + `StreamReader(stdin)`，再将 .NET string 传给 `Set-Clipboard -Value` | 保留成功的 OSC 52；两个 writer 都失败才报错 |
| macOS | `pbcopy` | 为 child 固定 UTF-8 locale；清除会覆盖 `LANG/LC_CTYPE` 的非 UTF-8 `LC_ALL`，设置受支持的 UTF-8 locale | 保留成功的 OSC 52；`pbcopy` 不可用/失败时按现有上限处理 |
| Linux Wayland | `wl-copy --type text/plain;charset=utf-8` | stdin 是显式 UTF-8 bytes，MIME 明确声明 charset | 继续尝试 X11 writer，再保留 OSC 52 |
| Linux X11 | `xclip -selection clipboard -target UTF8_STRING` | stdin 是显式 UTF-8 bytes，selection target 固定为 `UTF8_STRING` | 保留 OSC 52；均失败且 payload 超限时提示 `/export` |

实现要求：

1. 删除 win32/cygwin 的 `clip.exe` writer，复用现有 PowerShell reader 已建立的平台依赖。
2. PowerShell script 必须固定且不可被 clipboard 内容改变；clipboard 文本不得进入 argv、环境、日志、notice 或错误消息。
3. `spawn` seam 接收 UTF-8 `Buffer`，不再让 platform helper 猜测 JS string 的编码。不得使用 `shell: true`、字符串拼接命令或临时明文文件。
4. 保留 `windowsHide`、deadline、kill、stderr 丢弃和最大字节限制；macOS/Linux 也走同一个 bounded process runner。
5. `auto` 继续先发 OSC 52 再尝试系统 writer，以兼容 tmux/SSH/terminal emulator 吞掉 OSC 52 的情况；系统 writer 必须 Unicode-safe，不能再次覆盖成错误内容。
6. 返回实际成功链路：系统 writer 成功覆盖后，`finalMethod` 必须是该 writer，同时在 `succeeded` 中保留 OSC 52；不能继续把最终写入者误报成 `osc52`。
7. `fallback='osc52'/'off'` 的现有对外语义不得暗改；重构前先用 characterization test 固化。设置 schema 若仍把 `off` 表述为“禁用 process fallback”，README 英文/中文必须保持一致。
8. clipboard payload 为空、含 NUL/C0/C1/escape、超限时继续服从既有 copy/read threat model；本任务不增加任意 shell、远端 clipboard read 或自动执行 paste。

测试矩阵必须复用同一组 Unicode corpus，而不是三套彼此漂移的样例：

- ASCII：`plain text`。
- CJK：简体、繁体、日文、韩文混排。
- emoji：包含 ZWJ family、variation selector 和 skin tone。
- combining：预组字符与 combining mark。
- 换行：LF、CRLF、空行、无末尾换行。
- 边界：刚好/超过 OSC 52 byte limit，确保按 UTF-8 bytes 而非 UTF-16 code units 计数。

每个平台的 synthetic test 必须断言：command/args/env 固定、stdin 与 `Buffer.from(text, 'utf8')` 完全相等、payload 不在 argv/env/error、最终 method 正确、第一 writer 失败时按表回退、timeout 会 kill 且不会清除 UI selection。Linux 另外覆盖 Wayland→X11 fallback；macOS 覆盖非 UTF-8 父 locale 不得污染 `pbcopy` child；Windows 覆盖 strict decoder 和无 BOM 输入。

真实 clipboard round-trip 只能作为 opt-in 平台门禁：先保存用户 clipboard，测试 CJK/emoji/newline，最后在 `finally` 恢复；默认 unit、`pnpm test` 和 stock dsh cycle 不接触真实 clipboard。CI 没有图形 Session 时只跑 synthetic adapter tests，不能把无 DISPLAY/Wayland 当功能失败。

影响评估：

- 修复范围集中在 clipboard writer/runner 和测试，不需要修改 selection、context menu 或 terminal mouse protocol。
- PowerShell、`pbcopy`、`wl-copy`、`xclip` 启动成本只发生在显式 Copy；不增加常驻进程或 mouse input 延迟。
- 必须验证 Windows PowerShell 5.1/7、macOS UTF-8 locale、Wayland MIME 和 X11 `UTF8_STRING` 的固定参数；任一平台不满足时只回退，不猜编码。
- 原生 terminal copy 路径不受影响；OSC 52 继续是跨 SSH/tmux 的独立安全通道。

## 14. B10：选区跨 viewport 的逻辑锚点与边缘自动滚动

### 14.1 触发与根因

触发方式：在 full mouse 模式中从 Transcript 可见文字开始拖选，把指针停在窗口顶部或底部并等待视口滚动，再继续跨一页以上选择。旧行为最多稳定选择一个可见窗口，滚动后选区会停止延伸或锚点漂移。

根因不是虚拟化本身，而是选择状态混用了两类坐标：

1. `surface.ts` 每次 drag 都用最初的屏幕 `row/col` 重新命中 anchor；viewport 改变后，同一个屏幕单元对应了另一段文本。
2. `mouse-controller.ts` 的 edge-scroll timer 只调用 `transcript.scrollBy()`，没有把静止在边缘的指针继续投影为 selection focus；终端在鼠标静止时不会发送新的 motion。
3. 初次 edge tick 同步发生在 drag semantic 返回之前，Surface 尚未来得及建立文本 anchor，因而无法安全推进选区。

### 14.2 敲定实现

- 第一次有效 drag 同时记录 origin cell 的 `before`/`after` 两个 durable anchor（`ownerKey + textOffset + affinity`）。后续拖动只根据当前逻辑方向选择其中一个，绝不从已经滚动后的屏幕坐标重算 origin。
- edge-scroll 先等待一个 `EDGE_SCROLL_MS` dwell，再携带最后的指针位置回调；每个 tick 先把 focus 推进到当前 viewport 的首/末可选文本单元，再滚动并请求下一帧。
- Transcript 提供 viewport-edge anchor 和 durable-anchor ordering 公共语义；padding、短行和水平越界统一钳制到最近的可复制 cell。
- 高亮继续只对 `lastViewportMaps` 投影，禁止为选择而 render 全历史。复制从 durable selection 跨 owner 提取；跨页过程中访问过的 block 继续使用现有 width cache/`ownerCopy`。
- 新旧 Session、owner 删除、resize、FocusOut、模式切换、overlay 捕获和非鼠标输入会结束临时 pointer gesture，但不无故清除已经提交的 selection。prepend older history 若保留原 owner，则逻辑 anchor 继续有效。

### 14.3 测试与提交落位

- `mouse-controller.test.ts`：edge dwell 前不得滚动；dwell 后回调必须携带稳定 point；release/dispose 后 timer 为零。
- `transcript-viewport.test.ts`：同一 logical anchor 跨至少 3 个 viewport，最终 copy 同时包含起止页文本，且 `lastFullLinesCopied` 保持 0。
- `mouse-performance.test.ts`：继续证明 selection paint 只处理 viewport cells，不因历史长度线性放大。
- 人工验收：分别向上、向下跨页；在边缘停留速度随越界距离有界变化；中途反向越过 origin；松开后高亮和右键 Copy 保留；长 CJK/emoji/ANSI 文本不拆 grapheme。
