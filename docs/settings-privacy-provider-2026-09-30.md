# Native Settings, privacy and Provider write boundaries

The five terminal plugins mark only known schema fields volatile, using detached schemas. Actual published SettingsForms.replace/mutate tests show that ordinary unknown/legacy root config survives replacement and stale revisions are refused. Unknown root fields are not made live implicitly.

/privacy and /settings privacy read the current Profile and actual mounted session-log-deepseek/telemetry-otel instances by module identity and unique entry id. Only policy/limit scalars cross the bridge; no key, endpoint or Session data is read. Session log enabled is an official live field and stays in native Settings. Official rc.2 defaults: session-log enabled=true/maxBytes=8388608; OTel mode=FEEDBACK_ONLY, maxRequestBytes=4000000 in dsh-base. These defaults were read from the existing unmodified stock distribution; they do not assert the current user's policy or upload history. OTel mode is not volatile, so its change requires Profile config and restart. Desktop product analytics is separate and is not certified by this Host view. DSH_TELEMETRY_DISABLED is not a unified switch. Log disabling affects future requests; prepared payloads are not recalled, and re-enable may send unaccepted suffixes.

Provider key writes re-read the exact settings instance/path and credential metadata after Settings reconciliation. A redirected/missing/duplicate target, unavailable metadata or newly configured new Ref prevents the key write. Lost credential replies are unknown outcomes: metadata cannot verify secret equality, and the interactive flow offers no automatic retry. Synthetic tests confirm only one write/confirmation and no key in rendered content. The Host does not provide credential CAS: a concurrent mutation after the last read is still possible. This narrows the window without claiming atomicity. Existing explicit updates of configured keys retain user confirmation.

Validation: Node24.20.0, isolated HOME/XDG/DSH_HOME, 84 tests across 10 files, typecheck and diff-check passed. Actual SettingsForms writer and public privacy/Provider flows are exercised, not just source patterns. No real key/history, account or model request. Follow-up closes the independently reproduced non-default Provider-instance gap. The editor recognizes only native directory-addressed object profiles with the expected typed baseURL/model-id fields and optional typed credential/display/protocol fields. It uses the exact Host settingsNs/settingsPath and reads protocol options at that path, rather than assigning adapter semantics from the namespace spelling. Unknown/malformed schemas still fall back to generic Settings. Profiles without a declared API-key Ref field do not offer a fabricated credential edit.

Custom creation enumerates supported native providers dictionary schemas; multiple instances require explicit selection, and the single-instance path remains direct. A route writes only that selected Settings namespace and retains native revision/conflict handling. Public regression tests cover an alternate namespace with a different native path, creation in one of two instances without changing the other, and refusing an unknown schema.
