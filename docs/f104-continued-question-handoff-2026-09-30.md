## Safety and state interpretation

`continued -> submitting -> queued` is UI observation plus the real receipt, **not** durable completion. Only authoritative `settled` projection establishes admitted answers. Native `REPLY_QUEUED` stays queued. Unknown RPC, permission/transport failures after dispatch, cancellation, deadline, disconnect and generation replacement remain unknown; late success/error cannot override the observation. Fresh continued projection alone does not prove a previously dispatched answer is absent from native inbox, so refresh does not unlock that unknown outcome. There is no public reply-status query to resolve that ambiguity. A settled projection does resolve it. No automatic retries occur.

Page close before confirmation causes no write. Closing/cancelling progress after dispatch aborts only UI observation; the native unary has no cancellation parameter, so it may have queued already. It cannot cancel a persisted question or claim that a queued reply was removed. New separate client instances have independent observation maps; the native `REPLY_QUEUED` gate arbitrates cross-client duplicate submissions.

Foreground E follow-up (documentation only): existing `src/host/native-interactions.ts` ignores request `callId`/`timeoutMs` and accepts only generic cancelled failure mapping. E must carry the official timed request identity/lifetime through the foreground surface, attach the exact `attachWait` stream only while its open question UI exists, use Host `remainingMs`, and dispose the stream on page teardown/settlement/disconnect. Its timeout must reject the original foreground waterfall with authentic `UserQuestionError('…','ASK_TIMED_OUT')`; official `askTimed` maps that to `{pending:true,callId}`. `ASK_ABORTED` remains cancellation. Background `answer` cannot replace that original foreground response. This view deliberately makes no attachWait occupancy claim and does not alter that foreground core.
